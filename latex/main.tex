	\chapter{Introducción}
	El transporte público en el municipio de Cochabamba representa un pilar fundamental para la movilidad urbana diaria, siendo el sector estudiantil uno de sus usuarios más frecuentes. Para garantizar el acceso a la educación, normativas municipales establecen una tarifa preferencial y diferenciada para los estudiantes de nivel primario y secundario. Sin embargo, el método tradicional de cobro en efectivo dentro de minibuses y trufis genera constantes fricciones, retrasos y un cumplimiento irregular de dicha tarifa.
	
	El presente proyecto propone la modernización y digitalización de este proceso mediante el diseño y desarrollo de un ecosistema tecnológico cliente-servidor. La solución integra un sistema web (Backend) encargado de la gestión de usuarios y saldos virtuales, junto con una aplicación móvil Android que funciona como terminal de cobro (lector) y un sistema de tarjetas físicas provistas de tecnología NFC para los estudiantes. A través de este modelo, el sistema permite que el estudiante realice el pago de su pasaje de manera rápida, segura y totalmente offline al acercar su tarjeta al dispositivo del conductor, quien valida la transacción y recibe los fondos correspondientes en su cuenta virtual. De esta manera, se busca eliminar el uso de dinero en efectivo, garantizar el respeto a la tarifa estudiantil y proveer un registro auditable de los viajes realizados.
	
	\section{Antecedentes}
	
	Históricamente, en la ciudad de Cochabamba y a nivel nacional, el pago del transporte público descentralizado (sindicatos de trufis y minibuses) se ha realizado exclusivamente mediante dinero en efectivo. Si bien existen normativas municipales que amparan el derecho de los estudiantes a pagar una tarifa reducida, la aplicación práctica de esta medida presenta graves deficiencias. Es un escenario común que los conductores del transporte público se nieguen a cobrar el pasaje diferenciado argumentando la falta de cambio (monedas de baja denominación), o que directamente eviten recoger a los estudiantes en horarios pico para no percibir ingresos menores.
	
	A nivel tecnológico, en Bolivia existen referentes exitosos de modernización del transporte masivo, como el sistema "Mi Teleférico" o los buses "PumaKatari" en La Paz, los cuales utilizan tarjetas físicas RFID/NFC para el cobro automatizado con un alto grado de eficiencia y aceptación ciudadana. El uso de tarjetas físicas ha demostrado ser el método más accesible y rápido para el abordaje de pasajeros. Al adaptar este modelo exitoso al transporte descentralizado de Cochabamba, y complementarlo con el uso de los teléfonos inteligentes de los conductores como terminales de validación, se democratiza el acceso a los pagos digitales sin requerir instalaciones de hardware costosas dentro de cada vehículo.

	\subsection{Objetivo general}
	
	Desarrollar un sistema web y una aplicación móvil Android, integrando tecnología NFC, para la gestión y cobro eficiente del pasaje estudiantil en la ciudad de Cochabamba.
	
	\subsection{Objetivos específicos}
	
	\begin{itemize}
		\item Elaborar el modelo relacional de la base de datos para gestionar de forma íntegra y segura los perfiles de los usuarios (estudiantes y choferes), los saldos virtuales y el registro histórico de las transacciones.
		
		\item Diseñar el \textit{backend} del sistema en PHP bajo el patrón de arquitectura MVC, implementando un módulo de administración (CRUD) de usuarios y una API para el procesamiento de peticiones de cobro.
		
		\item Implementar un mecanismo de seguridad basado en tokenización (como JWT) para generar credenciales temporales, permitiendo que el pago desde el dispositivo del estudiante se realice de manera \textit{offline}.
		
		\item Programar el módulo de la aplicación móvil Android dirigido al estudiante, utilizando la tecnología de Emulación de Tarjeta Host (HCE) para transmitir de forma segura el token identificador vía NFC.
		
		\item Construir la interfaz (móvil o web) dirigida al chofer, encargada de activar el modo lector NFC, capturar el token del estudiante y comunicarse con el servidor para validar y ejecutar el descuento de la tarifa preferencial.
		
		\item Ejecutar pruebas de funcionamiento e integración entre las aplicaciones cliente y el servidor en un entorno local, verificando la velocidad de respuesta, la integridad de los saldos y el correcto manejo de errores.
	\end{itemize}

	\section{Arquitecturas de aplicaciones web}
	
	Según \citet{pressman2014}, la arquitectura de una aplicación web define la estructura general del sistema, estableciendo la manera en que los distintos componentes interactúan entre sí para proporcionar servicios al usuario final a través de la red.
	
	En el presente proyecto, la arquitectura web es fundamental debido a que el sistema propuesto se basa en un modelo cliente-servidor. La aplicación web funcionará como el backend encargado de gestionar usuarios, transacciones y saldos virtuales del sistema de pago del transporte estudiantil.
	
	\subsection{Aplicación web}
	
	De acuerdo con \citet{kurose2017}, una aplicación web es un software que se ejecuta en un servidor y que los usuarios pueden acceder mediante un navegador web utilizando protocolos de comunicación como HTTP.
	
	En el proyecto propuesto, la aplicación web constituye el núcleo del sistema, ya que será responsable de gestionar la información relacionada con los estudiantes, conductores y las transacciones de pago realizadas mediante la tecnología NFC.
	
	\subsection{Modelo cliente-servidor}
	
	Según \citet{tanenbaum2016}, el modelo cliente-servidor es una arquitectura de red en la cual múltiples clientes solicitan servicios o recursos a un servidor central que procesa las solicitudes y responde con la información correspondiente.
	
	En el sistema planteado, el dispositivo móvil del conductor y el sistema del estudiante actuarán como clientes que interactúan con el servidor central donde se almacenará la base de datos y se procesarán las operaciones de validación de pago del pasaje estudiantil.
	
	\subsection{Protocolo HTTP}
	
	Según \citet{kurose2017}, el protocolo HTTP (HyperText Transfer Protocol) es el protocolo de comunicación utilizado para la transferencia de información entre clientes y servidores dentro de la World Wide Web.
	
	En el desarrollo del sistema propuesto, HTTP permitirá que la aplicación móvil y la interfaz web se comuniquen con el servidor mediante solicitudes y respuestas que permitirán consultar información, validar usuarios y registrar las transacciones realizadas.
	
	\section{Tecnologías del lado del servidor}
	
	De acuerdo con \citet{pressman2014}, las tecnologías del lado del servidor son aquellas que permiten procesar la lógica de negocio de una aplicación web, gestionar bases de datos y generar respuestas dinámicas que son enviadas al cliente.
	
	En el presente proyecto, las tecnologías del lado del servidor permitirán gestionar la información de los usuarios del sistema, controlar el saldo de las tarjetas estudiantiles y registrar cada transacción realizada durante el uso del transporte público.
	
	\section{Entorno de desarrollo local}
	
	Según \citet{pressman2014}, un entorno de desarrollo local permite a los desarrolladores probar y ejecutar aplicaciones en su propio equipo antes de desplegarlas en un servidor de producción.
	
	Para el desarrollo del sistema propuesto se utilizará un entorno de desarrollo local que permitirá simular el funcionamiento completo del sistema web antes de su implementación en un entorno real.
	
	\subsection{Servidor local}
	
	Un servidor local es un servidor que se ejecuta en el propio equipo del desarrollador con el objetivo de probar aplicaciones web sin necesidad de conexión a internet \citep{tanenbaum2016}.
	
	En el desarrollo del proyecto, el servidor local permitirá ejecutar el sistema web, realizar pruebas de funcionamiento y validar la comunicación entre la aplicación móvil y el backend del sistema.
	
	\subsection{PHP}
	
	Según \citet{phpmanual2023}, PHP es un lenguaje de programación del lado del servidor ampliamente utilizado para el desarrollo de aplicaciones web dinámicas.
	
	En este proyecto, PHP será utilizado para desarrollar el backend del sistema, implementar la lógica de negocio y gestionar la comunicación con la base de datos.
	
	\subsection{MySQL}
	
	De acuerdo con \citet{mysql2023}, MySQL es un sistema de gestión de bases de datos relacional que permite almacenar, organizar y consultar grandes cantidades de información de manera eficiente.
	
	En el sistema propuesto, MySQL será utilizado para almacenar la información de los usuarios, tarjetas estudiantiles y registros de transacciones realizadas.
	
	\section{Intercambio de datos en aplicaciones web}
	
	El intercambio de datos es un aspecto fundamental en las aplicaciones web modernas, ya que permite la comunicación entre diferentes sistemas mediante formatos estandarizados \citep{kurose2017}.
	
	En el proyecto desarrollado, el intercambio de datos permitirá que la aplicación móvil y el servidor web compartan información relacionada con usuarios, saldos y registros de transacciones.
	
	\subsection{Formato JSON}
	
	Según \citet{ecma404}, JSON es un formato ligero de intercambio de datos basado en texto que es fácil de leer y escribir para los humanos y sencillo de procesar por las máquinas.
	
	En el sistema propuesto, JSON será utilizado como formato principal para enviar y recibir datos entre la aplicación móvil y el servidor web.
	
	\subsection{Web Service}
	
	Según \citet{erl2005}, un Web Service es un conjunto de funciones accesibles a través de la red que permiten la comunicación entre diferentes aplicaciones mediante protocolos estándar.
	
	En el proyecto propuesto, se implementará una API que funcionará como un servicio web encargado de procesar las solicitudes de validación y cobro del pasaje estudiantil.
	
	\section{Tecnologías de interacción cliente-servidor}
	
	Las tecnologías de interacción cliente-servidor permiten mejorar la experiencia del usuario al facilitar la comunicación dinámica entre el navegador y el servidor sin necesidad de recargar completamente la página \citep{garrett2005}.
	
	Estas tecnologías serán utilizadas en el sistema web para permitir consultas dinámicas de información y mejorar la eficiencia de la interacción con el sistema.

	En el sistema desarrollado, la arquitectura MVC permitirá organizar el código de manera clara, separando la gestión de datos, la lógica del sistema y la interfaz de usuario.

	Según \citet{ecma262}, JavaScript es un lenguaje de programación interpretado, ampliamente utilizado para el desarrollo de aplicaciones web interactivas tanto en el cliente como en el servidor.
	
	En el proyecto propuesto, JavaScript será utilizado para implementar la lógica del lado del cliente, permitiendo la interacción dinámica con el usuario y la comunicación con el backend mediante solicitudes HTTP.

	\subsection{Configuración de la base de datos} 
	La persistencia de datos se resolvió utilizando MySQL. A diferencia de un entorno completamente contenedorizado, Docker se empleó de manera exclusiva para levantar la instancia de MySQL, lo que garantiza que el motor de base de datos se ejecute en un entorno limpio y reproducible sin afectar los recursos del sistema anfitrión. Para ello, se definió la configuración del servicio en el archivo \texttt{docker-compose.yml} (ver Anexo A), ubicado en la raíz del proyecto, y se inicializó el contenedor ejecutando el comando \texttt{docker compose up -d} en la terminal.
	
	Una vez que el servicio de base de datos estuvo en ejecución, se procedió a establecer la conexión con el backend nativo de Laravel. Esto se logró modificando el archivo de configuración \texttt{.env} dentro del directorio \texttt{/backend}, donde se definieron las credenciales y parámetros de red mediante las siguientes variables de entorno:
	
	\begin{itemize}
		\item \texttt{DB\_CONNECTION=mysql}
		\item \texttt{DB\_HOST=127.0.0.1}
		\item \texttt{DB\_PORT=3306}
		\item \texttt{DB\_DATABASE=laravel\_db}
		\item \texttt{DB\_USERNAME=laravel\_user}
		\item \texttt{DB\_PASSWORD=secret\_password}
	\end{itemize}
	
	Finalmente, con la conexión a la base de datos exitosamente establecida, se procedió a estructurar el esquema de datos. 	\section{Arquitectura del sistema} 
	
	\subsection{Arquitectura cliente-servidor} 
	El sistema implementa una arquitectura cliente-servidor estricta, operando en repositorios y puertos separados. El servidor (backend en Laravel) actúa exclusivamente como un proveedor de servicios mediante una API, gestionando la lógica de negocio, la validación de las transacciones NFC para el pasaje estudiantil y la interacción con MySQL. El cliente web (frontend en Next.js) consume estos servicios de forma asíncrona y se encarga de la renderización de la interfaz administrativa e interactiva.
	
	\subsection{Patrón MVC en el backend} 
	Dentro del ecosistema del backend, Laravel implementa el patrón arquitectónico Modelo-Vista-Controlador (MVC). Dada la naturaleza de API del proyecto, la capa de "Vista" devuelve exclusivamente respuestas estructuradas en formato JSON. 
	\begin{itemize}
		\item \textbf{Modelos (\texttt{app/Models}):} Representan las entidades de datos (como Usuarios, Tarjetas NFC, Transacciones) y gestionan la relación con MySQL a través del ORM Eloquent.
		\item \textbf{Controladores (\texttt{app/Http/Controllers}):} Procesan las peticiones HTTP entrantes desde la aplicación Next.js y los dispositivos móviles, interactúan con los modelos y devuelven el estado de las operaciones.
	\end{itemize}
	
	\section{Estructura del proyecto} 
	
	\subsection{Organización de carpetas} 
	El proyecto está organizado dividiendo claramente el sistema en dos entornos separados: el \textit{backend} (API) y el \textit{frontend} (interfaz de usuario). En la raíz del proyecto se encuentra el archivo \texttt{docker-compose.yml} (destinado al despliegue de los servicios y la base de datos), acompañado de dos directorios principales.
	
	\subsection{Directorios principales} 
	A continuación, se describe la función de los directorios más relevantes de la aplicación:
	
	\begin{itemize}
		\item \textbf{\texttt{/backend}:} Contiene el núcleo de la API desarrollada en Laravel. Destacan las carpetas \texttt{app/} (lógica de negocio y modelos), \texttt{config/} (configuraciones globales), \texttt{database/} (migraciones de la base de datos) y \texttt{routes/} (donde \texttt{api.php} define los \textit{endpoints} del sistema).
		
		\item \textbf{\texttt{/frontend}:} Alberga la aplicación web desarrollada con Next.js, la cual está estructurada bajo una arquitectura modular orientada a dominios:
		\begin{itemize}
			\item \textbf{\texttt{app/}:} Define el sistema de enrutamiento mediante el \textit{App Router}. Separa las rutas públicas de autenticación dentro del grupo \texttt{(auth)} y las vistas administrativas protegidas dentro de \texttt{dashboard/} (cuentas, dispositivos, roles, transacciones y usuario).
			\item \textbf{\texttt{components/}:} Aloja los componentes visuales compartidos de la interfaz, incluyendo la navegación y el subdirectorio \texttt{ui/} para componentes base reutilizables.
			\item \textbf{\texttt{modules/}:} Constituye el núcleo de la lógica del frontend. Agrupa el código por dominios específicos (\texttt{auth}, \texttt{cuentas}, \texttt{roles}, etc.), encapsulando internamente sus propios componentes visuales, \textit{hooks}, esquemas de validación y servicios de conexión (\textit{queries} a la API).
			\item \textbf{\texttt{lib/} e \textbf{\texttt{hooks/}}:} Contienen utilidades transversales. \texttt{lib/} almacena configuraciones esenciales como los clientes de conexión (\texttt{api-client.ts}), y \texttt{hooks/} guarda ganchos globales de la interfaz.
		\end{itemize}
	\end{itemize}

	\section{Desarrollo de la aplicación}
	
\subsection{Definición de rutas e integración de la API}

El sistema implementa una arquitectura basada en servicios (API RESTful) que comunica el \textit{back\-end} (Laravel) con el \textit{front\-end} (Next.js). La definición de rutas abarca desde la exposición de \textit{end\-points} en el servidor hasta su respectivo consumo y validación en el cliente.

\subsubsection{Enrutamiento en el Backend (Laravel)}
La configuración de rutas se centraliza en el archivo \texttt{routes/api.php}. El diseño de la API sigue las siguientes convenciones principales:

\begin{itemize}
	\item \textbf{Autenticación y Seguridad:} Se exponen rutas públicas para el registro (\texttt{/register}) y acceso (\texttt{/login}). Por otro lado, las rutas que devuelven la sesión del usuario (\texttt{/user}) o ejecutan cierres de sesión están protegidas bajo el \textit{middle\-ware} \texttt{auth:sanctum}, garantizando que solo clientes con un \textit{token} válido accedan.
	\item \textbf{Controladores de Recursos (API Resources):} Se utiliza el método \texttt{Route::api\-Resource} para generar automáticamente las rutas CRUD (Crear, Leer, Actualizar, Eliminar) de entidades clave, tales como \texttt{users}, \texttt{roles}, \texttt{tarifas}, \texttt{cuentas} y \texttt{transacciones}.
	\item \textbf{Rutas Específicas de Lógica de Negocio:} Para procesos que no encajan en el modelo CRUD estándar, se definen \textit{end\-points} personalizados. Esto incluye la gestión transaccional (ej. \texttt{/cobro}, \texttt{/recargas}) y la obtención de relaciones complejas (ej. \texttt{/usuarios/\{id\}/cuenta}).
\end{itemize}

\subsubsection{Consumo en el Frontend (Next.js)}
En el lado del cliente, las peticiones HTTP se abstraen dentro de los módulos correspondientes. Tomando como ejemplo el servicio de usuarios (\texttt{usuario.api.ts}), el flujo de datos se maneja de la siguiente forma:

\begin{itemize}
	\item \textbf{Cliente HTTP Centralizado:} Se emplea una instancia personalizada llamada \texttt{apiClient} que se encarga de estandarizar las peticiones (inyectando \textit{headers} y manejando sesiones) hacia los \textit{end\-points} de Laravel.
	\item \textbf{Manejo Dinámico de Parámetros:} Para peticiones GET complejas como listados (\texttt{fetchUsuarios}), se utiliza la interfaz \texttt{URL\-Search\-Params}. Esto permite inyectar dinámicamente parámetros de paginación, filtros (\textit{estado}, \textit{rolId}), búsquedas (\textit{search}) y ordenamiento directo en la URL de la API.
	\item \textbf{Validación de Tipos Estrictos:} Para garantizar la integridad de la información que ingresa al estado de la aplicación, las respuestas en formato JSON se validan en tiempo de ejecución utilizando la librería Zod (ej. \texttt{usuario\-Response\-Schema.parse(data)}). Si la respuesta del servidor no coincide con el esquema esperado, se intercepta el error para evitar fallos silenciosos en la interfaz.
\end{itemize}

	\subsection{Creación de controladores}
	\begin{description}
		\item[UserController:] Para registrar, editar, suspender (Inactivo) a estudiantes, choferes y cajeros. Al crear un usuario, el controlador también debería crear automáticamente su Cuenta con Saldo 0.
		
		\item[TarifaController:] Para modificar los precios. (Si mañana la alcaldía sube el pasaje de 0.50 a 0.60, lo cambias aquí y todo el sistema se actualiza).
		
		\item[TarjetaNfcController:] Para asignar una tarjeta física (leer el \texttt{UID\_NFC}) y enlazarla al \texttt{Id\_Usuario} de un estudiante. También para cambiar su estado a 'Perdida' si el estudiante la reporta.
		
		\item[RecargaController (o CajaController):] La interfaz web donde el cajero recibe dinero en efectivo de un estudiante, busca su cuenta y le aumenta el Saldo (Generando una transaccion de tipo 'Recarga Saldo' con un \texttt{Id\_Cuenta\_Destino} nulo).
		
		\item[ReporteController:] Para ver métricas globales. ¿Cuánto se recaudó hoy? ¿Cuántos pasajes se pagaron?
		
		\item[RolController:] Para crear, borrar, actualizar y leer los diferentes roles.
		
		\item[AuthController:] Para que el chofer introduzca su correo/carnet y contraseña para abrir su turno en el celular. (Los estudiantes usarán esto si tienen una app para ver su saldo).
		
		\item[CobroController:] En la App Android del chofer lee una tarjeta y manda el \texttt{UID\_NFC} por POST a este controlador. \\
		\textbf{Lógica paso a paso:}
		\begin{itemize}
			\item Busca la Tarjeta\_NFC $\rightarrow$ verifica que esté 'Activa' $\rightarrow$ saca al Usuario dueño.
			\item Saca su Cuenta $\rightarrow$ saca el Rol $\rightarrow$ busca la Tarifa para ese rol.
			\item Descuenta el Monto del Saldo origen $\rightarrow$ lo suma al Saldo destino.
			\item Registra la Transaccion $\rightarrow$ devuelve un JSON: \\
			\texttt{\{"status": "ok", "msj": "Cobro exitoso", "saldo\_restante": 12.50\}}
		\end{itemize}
		
		\item[CuentaController:] Para tener un endpoint (ej. \texttt{GET /api/cuenta/mi-saldo}) donde un usuario pueda ver ya accedeetalles de su cuenta
	\end{description}
	
	\subsection{Creación de modelos}
	\begin{description}
		\item[Rol:] Relaciones: \texttt{hasMany(Usuario::class)}, \texttt{hasMany(Tarifa::class)}
		
		\item[Tarifa:] Relaciones: \texttt{belongsTo(Rol::class)} (Ej: Te dirá que el pasaje de 0.50 Bs le pertenece al rol 'Estudiante').
		
		\item[Usuario:] Relaciones: \texttt{belongsTo(Rol::class)}, \texttt{hasOne(Cuenta::class)} (Billetera única por persona), \texttt{hasMany(TarjetaNFC::class)} (Por si pierde una tarjeta y le dan otra).
		
		\item[Cuenta:] Relaciones: \texttt{belongsTo(Usuario::class)}, \texttt{hasMany(Transaccion::class)} (Como cuenta origen o destino).
		
		\item[TarjetaNFC:] Relaciones: \texttt{belongsTo(Usuario::class)}, \texttt{hasMany(Transaccion::class)}.
		
		\item[Transaccion:] Relaciones: \texttt{belongsTo(Cuenta::class, 'Id\_Cuenta\_Origen')} (Quien paga), \texttt{belongsTo(Cuenta::class, 'Id\_Cuenta\_Destino')} (El chofer/sindicato que recibe), \texttt{belongsTo(TarjetaNFC::class, 'UID\_NFC')}.
	\end{description}
	
\subsection{Desarrollo de vistas y componentes de interfaz}

El desarrollo de la capa visual del \textit{front\-end} se abordó mediante una arquitectura basada en componentes reutilizables, apoyándose en las convenciones del \textit{App Router} de Next.js y un sistema de diseño estandarizado.

\subsubsection{Estrategia de renderizado (Server y Client Components)}
Para optimizar el rendimiento y la experiencia del usuario, se implementó una separación clara entre componentes de servidor y de cliente:
\begin{itemize}
	\item \textbf{\textit{Server Com\-po\-nents} (por defecto):} Se utilizaron para las páginas estáticas y los \textit{lay\-outs} principales (como \texttt{app/dashboard/layout.tsx}). Esto permite que la estructura base de la aplicación se genere en el servidor, reduciendo el tamaño del paquete JavaScript enviado al navegador.
	\item \textbf{\textit{Client Com\-po\-nents}:} Aquellos elementos que requieren interactividad, manejo de estado local o el uso de \textit{hooks} (como los formularios de registro, tablas de datos interactivos y modales) se marcaron explícitamente con la directiva \texttt{"use client"}. Un ejemplo de esto son los componentes dentro de \texttt{modules/usuario/components/}.
\end{itemize}

\subsubsection{Sistema de diseño y librería UI}
Para mantener la coherencia visual y acelerar el desarrollo, se integró \textbf{Tailwind CSS} junto con una arquitectura de componentes base accesibles. 
La carpeta \texttt{components/ui/} actúa como una biblioteca interna donde residen elementos atómicos (\textit{botones, inputs, selectores, avatares, tablas y menús desplegables}). Estos componentes encapsulan sus propios estilos y comportamientos base, garantizando que vistas complejas, como los \textit{dash\-boards} administrativos, compartan el mismo lenguaje visual.

\subsubsection{Estructuración de Vistas Complejas}
Las interfaces principales, como el panel de administración (\textit{dash\-board}), se componen de varias capas jerárquicas:
\begin{enumerate}
	\item \textbf{Capa de Envoltorio (\textit{Layouts}):} Proveen el esqueleto de navegación persistente, integrando componentes globales como \texttt{app-sidebar.tsx} y \texttt{nav-main.tsx}.
	\item \textbf{Capa de Página (\textit{Pages}):} Actúan como contenedores principales de cada ruta (ej. \texttt{cuentas/page.tsx}).
	\item \textbf{Capa de Dominio (\textit{Módulos}):} Las páginas delegan la presentación de la información a componentes especializados del dominio, como \texttt{cuentas-data-table.tsx}, los cuales gestionan la paginación, filtros y acciones directas sobre los registros.
\end{enumerate}

	\section{Validación y manejo de errores}
	
	La robustez del sistema se garantiza mediante una estrategia de validación de doble capa (cliente y servidor) y un flujo estandarizado para la captura y presentación de errores, asegurando la integridad de los datos y una buena experiencia de usuario.
	
	\subsection{Validación de formularios}
	La validación de la información introducida por el usuario se divide en dos frentes:
	\begin{itemize}
		\item \textbf{Capa del Cliente (\textit{Front\-end}):} Se utiliza la integración de \textbf{React Hook Form} junto con \textbf{Zod}. React Hook Form gestiona el estado de las entradas minimizando los re-renderizados, mientras que Zod proporciona validación de esquemas con tipado estricto (\textit{type safety}). Los esquemas, como \texttt{usuario.schema.ts}, definen reglas precisas (longitud mínima, formatos de correo, campos obligatorios) y bloquean el envío del formulario si no se cumplen, proporcionando retroalimentación visual inmediata.
		\item \textbf{Capa del Servidor (\textit{Back\-end}):} Laravel actúa como la fuente de verdad definitiva. Utiliza sus clases \texttt{FormRequest} o validaciones integradas en los controladores para verificar nuevamente los datos entrantes. Esto previene la inyección de datos maliciosos en caso de que las validaciones del cliente sean eludidas.
	\end{itemize}
	
	\subsection{Manejo de excepciones}
	El manejo de excepciones se ha estructurado para interceptar fallos tanto lógicos como de red, evitando que la aplicación se detenga abruptamente:
	\begin{itemize}
		\item \textbf{Excepciones de Red y API:} En el cliente, el servicio centralizado (\texttt{apiClient}) captura códigos de estado HTTP de error (4xx y 5xx). Si la respuesta indica un fallo (ej. \texttt{!res.ok}), se lanza una excepción controlada (\texttt{throw new Error(...)}) que interrumpe el flujo normal.
		\item \textbf{Excepciones de Tipado de Datos:} Se implementa un bloque \texttt{try-catch} al procesar las respuestas del servidor. Si la estructura del JSON devuelto por Laravel no coincide con el esquema esperado en Next.js, Zod lanza un \texttt{ZodError}, el cual se registra en la consola para facilitar la depuración, previniendo fallos silenciosos en la interfaz.
	\end{itemize}
	
	\subsection{Control de errores}
	Una vez capturada una excepción, el sistema debe reaccionar de forma predecible y amigable para el usuario final:
	\begin{itemize}
		\item \textbf{Límites de Error (\textit{Error Boundaries}):} En Next.js, se hace uso de los archivos \texttt{error.tsx} en rutas específicas. Estos actúan como límites de error de React, aislando el fallo a un componente o vista particular en lugar de colapsar toda la aplicación.
		\item \textbf{Respuestas estandarizadas del Servidor:} Laravel está configurado para devolver siempre las excepciones de la API en formato JSON estandarizado, incluyendo un mensaje descriptivo y, en caso de errores de validación (HTTP 422), un desglose de los campos afectados.
	\end{itemize}
	
	\section{Pruebas del sistema}
	
	\subsection{Pruebas de funcionamiento}
	Para validar la correcta operatividad y la integración entre el \textit{front\-end} y el \textit{back\-end}, se ejecutaron pruebas funcionales enfocadas en los flujos críticos de negocio:

	\section{Resultados}
	
	\subsection{Funcionamiento final}
	El desarrollo del sistema concluyó con la exitosa integración de la arquitectura cliente-servidor propuesta. Se logró establecer una comunicación fluida y segura entre la interfaz de usuario (\textit{front\-end} en Next.js) y la API RESTful central (\textit{back\-end} en Laravel). 
	
	Entre los resultados técnicos y funcionales más destacados de la implementación se encuentran:
	\begin{itemize}
		\item \textbf{Gestión integral de dominios:} Los módulos principales (usuarios, roles, dispositivos, cuentas y transacciones) operan correctamente de extremo a extremo. Las operaciones de lectura, escritura y actualización mantienen una estricta integridad referencial en la base de datos PostgreSQL.
		\item \textbf{Seguridad y control de sesiones:} El flujo de autenticación basado en \textit{tokens} (vía Laravel Sanctum) protege eficazmente las rutas del cliente. El enrutamiento de Next.js bloquea exitosamente el acceso a los \textit{dash\-boards} administrativos si no existe una sesión activa y válida.
		\item \textbf{Rendimiento y experiencia de usuario (UX):} La arquitectura de Next.js, combinando \textit{Server Components} para la estructura base y \textit{Client Components} para interactividad (como las tablas de datos de transacciones), resultó en tiempos de carga óptimos. Además, el sistema de validación de doble capa con Zod demostró ser efectivo para prevenir la entrada de datos corruptos sin degradar la experiencia del usuario.
	\end{itemize}
